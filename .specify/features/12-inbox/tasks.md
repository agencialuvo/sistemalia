## Fase 2: Backend API & Messaging Service
- [x] **Task 2.1:** Crear `InboxModule`, `InboxController`, `InboxService` y `MessagingSenderService`. — `MessagingSenderService` resuelve la API destino por `SocialChannel.provider` (spec plan §3): Messenger/Instagram vía `POST /me/messages`, WhatsApp vía `POST /{phoneNumberId}/messages` (el `phoneNumberId` viene de `channel.metadata`, guardado por `SocialChannelsService.connectWhatsApp` en Feature 10).
- [x] **Task 2.2:** Implementar la ingesta en Webhooks de eventos `messages` para crear o recuperar `Conversation` y guardar el `Message` de entrada. — `InboxIngestionService` (nuevo), inyectado en `MetaWebhooksController` (Feature 10) igual que `MetaLeadProcessorService`: `entry.messaging[]` para Messenger/IG, `changes[].value` con `field: 'messages'` para WhatsApp — ambos disparados sin `await` (fire-and-forget, contrato <200ms del webhook). Vincula automáticamente con `Patient`/`Prospect` existente por teléfono cuando el proveedor lo entrega (WhatsApp sí; Messenger/IG solo dan un PSID/IGSID, no un teléfono real). Filtra `message.is_echo` para no duplicar como INBOUND los mensajes que este mismo Inbox ya envió.
- [x] **Task 2.3:** Implementar el endpoint `POST /marketing/inbox/conversations/:id/messages` para enviar respuestas hacia las APIs de Meta/WhatsApp. — Si `MessagingSenderService` falla, igual se guarda el `Message` con `status: 'FAILED'` (visible en el hilo) antes de relanzar el error. **Gap documentado:** solo texto — el envío de adjuntos (RF-2) requiere mapear cada tipo a la forma que exige cada Graph/WhatsApp API distinta, no solo guardar una URL como sí hace la ingesta INBOUND; queda para un incremento futuro, mismo criterio que el gap de `notes` en Prospect (Feature 11).
- [x] **Task 2.4:** Implementar listado y actualización de estado/asignación de conversaciones. — `GET /marketing/inbox/conversations` (paginado, ordenado por `lastMessageAt desc`, filtros search/status/provider), `GET /marketing/inbox/conversations/:id` (incluye mensajes ordenados asc), `PATCH /marketing/inbox/conversations/:id` (status/assignedUserId, `null` desasigna).

Este módulo nuevo vive en `src/lib/marketing-inbox/`, `src/hooks/use-conversation-directory.ts` y `src/components/marketing/inbox/` (namespace i18n `"UnifiedInbox"`) para no colisionar.

## Addendum (reorganización de IA a pedido del usuario)
La vista se movió de `/marketing/inbox` a `/bandeja-entrada`, y de labelKey `unifiedInbox`/grupo "Marketing" del Sidebar a "Principal" (debajo de "Panel") — el módulo pasó a llamarse "Bandeja de entrada" en el menú. `/marketing/inbox` quedó como redirect a `/bandeja-entrada` (mismo criterio que `/citas` -> `/agenda`). La Bandeja legacy de `/bandeja` (Supabase, wacrm original) perdió su entrada de menú en este mismo cambio — a pedido explícito del usuario de que solo quede UNA "Bandeja de entrada" visible en el Sidebar — pero su página y código NO se borraron: sigue siendo un deep-link válido desde el feed de actividad del dashboard, notificaciones y el formulario de deals (6 archivos la referencian, con un modelo de datos de Supabase incompatible con este módulo), así que eliminarla de raíz habría roto esas pantallas. Componentes/hooks/lib de este módulo (`src/lib/marketing-inbox/`, `src/hooks/use-conversation-directory.ts`, `src/components/marketing/inbox/`) no se renombraron — solo la carpeta de ruta bajo `src/app/(dashboard)/`.
